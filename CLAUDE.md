# break FAST — Project Intelligence File

Read this file before touching any code. It captures product decisions, rules, and architectural choices that aren't obvious from the code alone.

---

## What Is break FAST?

An AI-powered breakfast planner for home/trusted circle use. It knows each user — their ingredients, health context, habits, and kitchen — and uses that to suggest the richest, healthiest, most efficiently prepared breakfast each morning with minimal friction.

Multiple users share one instance, each fully isolated. Auth is a name and a PIN (salted scrypt hashes, rate-limited logins), managed by admin CLI. Accessible via Tailscale.

## Core Design Principles

**Reduce morning decision fatigue.** The app suggests proactively. If it needs info, it asks one question at a time.

**Health-aware, silently.** Health rules are per-user, stored in DB, injected into prompts at runtime. Never mentioned to the user. The app just makes good choices.

**Everything ready at once.** The prep planner breaks each cooked dish into its real steps, in order, one action each (usually a few): the action with the menu's ingredients and amounts, its minutes, hands-on (whisk, chop, flip, plate) or waiting (boil, toast, bake), and an optional appliance from the user's list. The LLM only decomposes and estimates (`routers/scheduler.py` asks it and caches the plan); `_build_plan` in `services/prep_plan.py` does the math. It schedules backwards from the finish so the dishes are ready together: each dish's steps stay in order, one cook does the hands-on steps one at a time, an appliance holds one step (the Stove two pans), and waiting steps need no cook, so other dishes' hands-on steps fill them. A dish's consecutive hands-on steps are one block, placed whole, so the cook switches dishes only at waits: another dish's block fills a wait or goes before or after it, a wait may start during a block's last step (put the bread in while the omelette sets) but not earlier in it, so the list never splits a block, and on a tie the dish just placed goes on. Whole blocks can make the one-pass plan much longer, so a short search (limited discrepancy, at most `_SEARCH_NODES` placements, off the event loop) tries other orders and keeps a shorter plan, or one as short where hot food sits less (`_hot_sitting`: a dish made with a hot appliance, `hot` in `KITCHEN_APPLIANCES`, waiting after it's done, and food from a hot step such as toast waiting for its dish's next step; a dish made without one, like a chia pudding, keeps and may be made first), then one with fewer switches; on random menus a plan is at most a few minutes longer than one that splits blocks (#152). Estimates code can't use get a default (a missing or non-positive minute count, an appliance outside the user's list, a missing hands_on). The plan is one list in time order under `⏱ Plan (N min)`: a time line (h:mm) names its dish before the step, the dish's steps that follow right after it sit under it as `↳` lines, a dish stops at a wait for another dish's steps and picks up again later (on a tie in the list a wait comes first, so the block it starts with stays together), waiting steps show their minutes and appliance, and the Ready line ends it. Code keeps colons out of dish names, so the app reads a time line's dish as the text before its first colon and colors it (`PrepPlanText`). Cached plans (`meal_history.schedule`) keep their old text. The planner gets only what the menu lists: each dish comes with its `method` in brackets after its name, and so does a simple item that is cut or cooked, listed as a dish of itself ("- Sweet potato (peel, cube and roast): Sweet potato (300 g)", #156), and an item served with or on another one names it there too ("- Tahini dressing (mix; serve with Omelette): …", #263); each food is cooked the way its method says, and items served as they are (no method) get no steps. A heating step names any appliance from the user's list that does the job, since code serves food from a hot appliance last, and the request ends with the order rule (the 7B model follows the last message best): within a dish, the prep that keeps (slicing, chopping, mashing, mixing) comes before the heating, and the heating as late as the dish allows, so hot food doesn't wait for the prep (#160); a method that names the heating first still keeps its order. The prompt's example plan is placeholders only (the 7B model copied its food into real plans). User's configured appliances (from Kitchen Settings) are injected into all LLM prompts.

**Local-first, free forever.** Primary LLM is Ollama on the user's own hardware. Song lyric fallback when unreachable.

**The system learns.** Stated habits are a warm prior. Actual behavior updates what gets recommended. The patterns come from the last 30 days of logged meals (`PATTERN_DAYS` in `services/insights.py`), each counted from its menu as eaten; nothing is deleted automatically, and Settings can delete meals older than a month.

## Architecture

```
[Phone / Desktop — browser]
         |  HTTP / WebSocket
         v
[FastAPI Backend — third PC]
   |               |
   v               v
[Ollama]    [Song lyric fallback]
   |
   v
[SQLite — breakFAST.db]
```

**Chat sync across devices:** `services/chat_sync.py` keeps each user's open chat sockets in memory (one server process, no polling) and drops a socket on disconnect. When a session's messages change (a typed message or a chat reply is saved, or a message is saved or edited over REST: meals sent to chat, analysis and prep plan results, meal card edits, which rewrite the message's JSON meal block, a card's saved "Today I ate" version, and the selected meal card), the server sends `{type: 'session_updated', session_id}` to that user's sockets only. A reply skips the socket that asked, and tokens never go to other devices. `ChatInterface` reloads the chat on screen on that push, when the page becomes visible again, and when its socket opens. A reload waits for a reply on its way into the chat on screen, a running analysis, a Stop the server hasn't confirmed yet or a session button (below), and keeps the draft and unchanged cards. Each typed message or Suggest press runs as a task on the server (`services/chat_tasks.py`), one per user at a time across all their devices: a slot kept in memory like the sockets, taken before the task starts and freed however it ends (finished, failed, stopped, or saved after its device dropped; a test fixture fails any test that leaves one taken). A message or press while one runs gets a short note in the reply language (`BUSY_TEXTS`) that reaches no model and isn't saved, like the too-long note. Stop sends `{type: 'stop'}`: the server cancels the device's task, which closes the model call's HTTP connection so Ollama stops, saves no reply, suggestion or selected card, and then answers `{type: 'stopped', session_id}`, so every frame of the stopped request comes before it. A typed message is saved when it arrives (after the history the chat persona reads), so it stays after Stop and other devices show it while the reply is made; a Suggest press saves its text only with its reply, so a stopped one leaves nothing. Once the reply is made its save runs whole, and a Stop then waits for it. A reply whose device drops mid-stream without Stop still finishes and is saved. On screen, Stop keeps what came so far with a small "Stopped" note (on this device, not saved; it goes at the next reload), nothing when nothing came, and drops the stopped request's frames until `stopped` arrives; a reply saved before the server read Stop reloads the chat then. Every reply frame (token, progress, done, meal card, error, a note) carries its chat's `session_id`, and the app shows a reply only in the chat it was sent from: switching chats mid-reply never moves it, the words so far show again on the way back, and a reply that finished meanwhile loads with that chat. The device's own request keeps Stop on screen in any chat until it ends. The chat's session buttons (New, Delete, Back, Next) run one at a time, off while one runs, and Back and Next are then read again from the server's list, each shown only when there's a chat to move to; New on a chat with nothing in it stays there, and Delete on the only chat starts a fresh one. Messages are saved only in the user's own sessions: the session endpoints take typed bodies (role `user` or `assistant`, text content; 422 otherwise) and a save to any other session gets 404, and the socket uses a frame's `session_id` only when it's one of the user's (a message frame falls back to the current session, then the latest, so it still gets its reply). The selected meal card (today's meal) is the same on every device: `chat_sessions.selected_message_id`, set with `PUT /sessions/{id}/selected` (a tap on a selected card's box unselects it), by a new suggestion, by a meal sent to chat (`select: true` on its POST), and cleared when the meal is logged; GET messages marks it `selected`.

Other changes send a small notice through `notify_user`: a supplement change or a pill marked for today sends `{type: 'supplements_updated'}`, and a shopping suggestions list change (bringing back removed suggestions included) `{type: 'shopping_suggestions_updated'}`. All tabs stay mounted, so the chat socket is open while the app is: `ChatInterface` passes every notice that isn't about the chat to the rest of the app as one window event (`hooks/useSyncNotice.js`: `emitSyncNotice`, `useSyncNotice(types, handler)`), plus `{type: 'sync_connected'}` when its socket opens, so a panel can catch up on what it missed. The supplements list in "Today I ate" reloads on a supplements notice, when the socket opens and when the page becomes visible; Settings reloads only its supplement list, so an unsaved profile edit stays. The Fridge tab reloads its suggestions list the same way, and Settings its count of removed suggestions. That list starts collapsed under a theme-colored bar as big as Suggest Shopping (title and count in the middle, ▲ while closed and ▼ while open at the right); while open, two helpers at the left check or uncheck every item and clear the list after an "Are you sure?" (cleared items aren't left out of later suggestions, unlike ×).

## Meal Format

LLM returns a full menu, not a single dish:

```json
{
  "menu_name": "Klasik Kahvaltı",
  "menu": [
    { "name": "Menemen", "method": "Biberi ve domatesi kavur, yumurtaları ekleyip karıştır", "ingredients": [
        { "name": "Yumurta", "amount": 2, "unit": "adet", "prep": "çırpılmış" }
    ]},
    { "name": "Beyaz peynir", "amount": 50, "unit": "g", "ingredients": [] }
  ],
  "prep_time_min": 15
}
```

- Complex dish: no top-level `amount`, has `ingredients[]`
- Simple item: has `amount` + `unit`, `ingredients: []`
- A dish may carry an optional `method`: its main steps in one short line, in the reply language ("Hard-boil the eggs, peel, slice into the bread"). It is stored with the dish in `menu_items` (older meals have none), and the prep plan gets "- Egg sandwich (Hard-boil the eggs, …): Egg (2 pcs), Bread (2 slice)". The draft prompt doesn't ask for it (with a method rule the prompt test scored worse: more renamed items and unknown units); the pipeline's reviser writes it for every dish through structured outputs (#121, #122). A simple item carries one too when it's cut or cooked (how it's readied), and none when it's served as it is (#156). A method fits only the food it was written for: once an editor edit adds, removes or renames a dish's ingredients (amounts, units and prep words don't count), ℹ️ stops showing it and the save drops it, so the plan follows the ingredients (#268)
- `nutrition_note` is no longer asked for (nothing showed it); older meals keep theirs
- A dish ingredient may carry optional `prep` words: the form the cook gives it when the dish needs that choice (how it is cut, which part, how it is cooked first: "diced", "whites only", "fried"), none when the form is obvious, since the planner turns them into steps. The reviser keeps the draft's, and the method tells the plan the rest: a check of them, in its system prompt or at the end of its message, dropped a word that changes nothing only once in four runs and then made the 7B model add ones (#176). The name stays exactly the fridge name, and the prep plan gets "Oats (1 glass, rolled)"
- A dish ingredient may carry optional `replaces`: the missing item the review swapped it in for (#148). Code keeps it only when that item was missing in the draft, the ingredient is in the fridge, and the item is gone from that dish; a simple item carries none. MealEditor shows a small ✱ beside the ingredient's name and a line in ℹ️ ("Feta: instead of Salmon (not in your fridge)"), and `menuKey` ignores it
- A menu item (simple item or dish) may carry optional `serve_with`: the name of another item on the same menu it's served with or on, for an item nobody eats on its own (#263). Stored in `menu_items` like `method` (older meals have none), written by the reviser only, and `menuKey` ignores it. After the review code reads it against the final menu (`resolve_pairs` in `services/pipeline.py`): it follows a partner the review renamed (found by its food), drops the paired item when its partner is gone (left out or moved into a dish, chains too), and clears any other pairing that names no other item, keeping the item. The plan input and the editor show a pairing only while it names another item of the menu (`paired_item` in `services/fridge.py`), and deleting an item in the editor clears the pairings to it
- MealEditor shows each dish's method and prep words, and a simple item's method, behind an ℹ️ button beside the prep time
- A meal may carry an `emoji`, its icon (#244): the pipeline gives the final meal one at random from `BREAKFAST_EMOJIS` (`with_emoji`, `models/meal.py`, mirrored in `utils/emoji.js`: edit both) once, so every device and reload shows the same one, and a meal that has one keeps it. Favorites store it (`favorite_meals.emoji`; an edit sent without one keeps the saved one); an older card without one shows one from its name, an older favorite one from its id (`mealEmoji`). Meal history has none
- `isSimpleItem(item)` = `item.amount != null`
- DB column `menu_items TEXT` on `meal_history`, `suggested_meals`, `favorite_meals`
- Old flat-format meals still work via `normalizeMeal()` in frontend

## LLM Personas

All in `backend/services/personas/`. Prompts are in English; the response language follows the user's setting (English default, Turkish option) — don't remove the Turkish path.

| Persona | Job | Temp | File |
|---|---|---|---|
| Chat | Casual breakfast buddy | default | `chat.py` |
| Suggestion | Creative meal designer (favorites/explore modes) | 0.6/0.9 | `dietitian.py` |
| Analyst | Nutrition calculator | 0.3 | `analyst.py` |
| Pipeline Analyst | Internal reviser: returns the fixed meal (structured outputs) | 0.3 | `pipeline_analyst.py` |
| Shopping | Professional shopping advisor | 0.6 | `shopping.py` |
| Scheduler | Kitchen step decomposer (steps per dish) | 0.3 | `scheduler.py` |
| Weekly Analyst | Holistic 7-day nutrition review (4 scores, nutrients lacking / more than enough; structured outputs) | 0.3 | `weekly_analyst.py` |

**Chat persona:** responds in plain text only. It talks with the user and helps them work out what they want this morning, one question at a time, and leaves dishes, recipes, amounts and cooking steps to the Suggest button, which builds a card they can edit, plan and log and follows what they wrote (#168). That rule rides in a note after the user's words in each message the chat persona gets (`CHAT_TURN_NOTE`, `build_chat_message` in `services/personas/chat.py`, ending with the reply language), never saved or shown: the 7B model follows the last message better than the system prompt, and with the rule there alone it answered almost every message with a dish idea and never pointed to Suggest. Meal blocks come only from the Suggest button, never from chat: code drops a chat reply's meal block before it's sent and saved, cut where the app stops showing it while it streams (`drop_meal_block` in `services/chat_block.py`; a reply that was only a block becomes `CHAT_SUGGEST_TEXTS`), and the chat's history shows each meal card as its one line (`chat_history`), since the 7B model copied a card's JSON into every reply after a Suggest press.

**Suggestion persona:** drafts the menu through Ollama structured outputs (`draft_schema` in `services/pipeline.py`: `{"text": ..., "meal": ...}`, its own words first so it plans the menu in words, then the meal in the reviser's item shape without a method; the text is shown only as the note below) and, in the pipeline's last step, writes the short reply text from the final meal alone (`build_present_prompt`: the menu name, one sentence, an optional taste tip; only items on the menu, no nutrition claims or prep steps). Must build meals from the fridge inventory only, basics like salt and oil included; a missing recipe item may be replaced with an inventory item, never with something outside it. A simple item is one fridge item served as it is; anything cooked, combined or with a sauce is a dish with its ingredients. The prompt's JSON example shows the format only (placeholders), and the rules carry no example dish or ingredient lists, because the 7B model copies examples into menus. Favorites mode asks for a menu that fits the user's taste, weighing every hint together without tying it to one: it lists the newest 10 meals saved in Favorites (`fetch_favorite_meals` in `services/context.py`, each as its name and one plain item list, since the 7B model copied a "Dish (items)" shape into dish names), the staples and the item ratings, beside the preferences, habits, patterns and recent meals the prompt already has. A saved meal may be made as it is or inspire something close to it, and the fridge rule is unchanged. When the latest weekly analysis ran in the last 7 days and marked something, the draft gets its nutrients as one hint line below the health rules (and the avoid list), never shown to the user: "Nutrients in recent breakfasts, estimated from logged meals (weigh with the other hints): lacking protein, fiber; more than enough sugar, salt." (`format_nutrients` in `services/knowledge.py`, the context's `nutrients`); a list with nothing marked is left out, and the line too when nothing is. Nutrient names stay in English like the prompts. The Settings weekly-summary switch governs only the weekly narrative; the nutrient line is always on. The chat persona doesn't get it (#206).

**Suggestion pipeline:** Draft → Revise → Present, three calls, and the reply keeps its shape (text, then the ```json meal block). Code puts the draft's meal in the app's format like the reviser's (below) and checks it (fridge, avoid list, units: `services/fridge.py`, `models/units.py`), and the reviser (Pipeline Analyst) gets that meal, code's findings, the avoid list, dislikes and the Suggest mode (favorites: keep it familiar, a saved meal is a hint; explore: keep it new). It fixes what code found, its only list of what's missing (a name that is a fridge item with only a cut or shape added, or with words left out, becomes the fridge name with the cut in `prep`; any other missing item, a part such as egg whites included, is swapped only for a fridge item that does the same job in that dish, with `replaces` naming it inside a dish, and otherwise, or when the reviser isn't sure, kept as written for the app to mark, since a rename to the whole item loses the part), answers narrow questions whose usual answer is no change (a top-priority health rule, a disliked item, a portion far off, an item nobody eats on its own, a dish or not, which moves into the dish it goes in, is paired with the item it's served with or on through its `serve_with`, filled beside the method, or is left out only when it goes with nothing on the menu, #263; and, with the weekly nutrient line, which it gets below the avoid list and dislikes, whether the menu leans hard on a nutrient that was more than enough or misses an easy fridge fix for one that was lacking, #206), and returns `{"changes": [...], "meal": {...}}` through Ollama structured outputs (`revision_schema` in `services/pipeline.py`: one item shape with the ingredients before the name, numeric amounts with units from the app's list on every item and ingredient, a dish ingredient's name limited to the fridge's names, the draft's own and water (`reviser_names`, an enum, so a swap brings in only what the user has; item names stay free for a dish renamed after a swap), an optional `replaces` limited to the draft's missing items, a method, and a `serve_with` limited to the draft's item names or empty, a closed list so no typo or made-up name gets in, read against the final menu by `resolve_pairs`; code drops a dish's own amount and unit and empty methods, and turns a one-item dish named as itself back into a simple item, keeping its method. Offered a choice of shapes, the 7B model dropped a dish's ingredients). The review may only improve the meal: if the revised meal can't be read, or code counts more avoid-list hits in it than in the draft, or as many and more fridge misses or unknown units, the draft's meal is used. The present step then writes the text from the chosen meal alone; when it fails, code writes the menu name and description. When the fridge is too small for a breakfast, the draft leaves `menu` empty and its text is a note that says what to change (add items in the Fridge tab, try the shopping suggestions), sent without a review; an empty menu without a note gets code's low-ingredients text (`LOW_INGREDIENT_TEXTS`), so the user knows to buy something. Any other press that ends without a meal, a draft reply that still can't be read or a pipeline that fails or says nothing (a timeout), gets "press Suggest again" in the reply language (`RETRY_TEXTS`), so the user sees it failed; only Ollama being unreachable gets a lyric. None shows a meal card, and nothing retries on its own, so the user's next press is the retry (#163). The reply is sent once the meal is chosen, not streamed. Code never removes items from a suggested menu: something the user doesn't have keeps its yellow mark so they can obtain it, and better menus come from the prompts. The one exception is an item paired with one the review left out, which goes with it (#263). Progress sent via WebSocket `{type: 'progress'}`.

**After a chat** every suggestion step follows what the user typed (#161). On a Suggest press the server reads the session (`services/chat_block.py`, so every device and reload sends the same) and builds one block in chat order, oldest first: the user's typed messages, never the Suggest buttons' text (`SUGGEST_MESSAGES`, mirrored in `ChatInterface.jsx`, which doesn't show them either: a press shows only its progress, on the user's side, until its card arrives), and the meal cards as they are now, edits included (name, dishes, items, one line each); nothing else the app wrote (chat replies, analyses, prep plans). The entries are numbered in chat order (`#1` oldest), the latest typed message is marked, and only a chat longer than `CHAT_BLOCK_CHARS` loses its oldest entries. The block's header gives the reasons: the user's words come before habits, favorites and patterns (health rules and the avoid list still hold), a later message wins over an earlier one and a message right after a menu is about it, an ask holds for every later menu as closely as the fridge allows, and a new menu differs from the ones shown. The draft and the reviser both get the block last in their message; the reviser's reply then starts with `chat_asks`, what the chat asks for now, latest first: each item lists the entries it comes from (`from`, a menu included when a message right after it is about it) before what holds now (`ask`), so a later message is read together with the earlier one it changes ("Actually simit is fine again" with "no simit") and the latest wins. It's one general list, no field per kind of request, and the review lists the asks with their entries. A fresh press sends no block, so its prompts are unchanged. Code checks nothing new: a chat can ask anything.

**Shopping persona:** suggests products you can buy, never dishes (a dish becomes its missing ingredients). Names are plain and specific, and every word names the product: "Frozen strawberries" is a different item from "Strawberries", while filler like "fresh" doesn't belong in a name. The reply is constrained by Ollama structured outputs (`SUGGESTIONS_SCHEMA` in `services/shopping.py`, sent by `chat_json` in `services/llm.py`; needs Ollama 0.5+), and the raw reply is logged when it still can't be parsed. Code then drops anything in the fridge, on the shopping list, already shown, on the avoid list or removed from the suggestions list in the last 7 days (`recently_removed`) by exact name (`same_name` in `services/fridge.py`: case, Turkish letters and plurals only), and asks once more when a whole reply was repeats. The removed items are left out by code only, so the prompt stays the same; after 7 days they may come back, and the avoid list is the permanent ban. Settings → AI settings → Removed shopping suggestions → **Bring back (N)** forgets them sooner, after an "Are you sure you want to allow N removed items back in suggestions?" prompt: `GET /shopping/suggestions/removed` counts what's left out now (the `recently_removed` rule), and `DELETE` removes the user's removed rows only, so the list on screen and the avoid list stay. Code also drops names that aren't one product ("Leafy greens (e.g. spinach)", "X or Y"; the prompt asks for alternatives as separate items next to each other) and the user's own dishes (`dish_names`: meal names and menu items made with ingredients, from all logged and favorite meals; simple items stay products). That filter is a safety net: the prompt asks for a dish's missing ingredients instead of the dish. The request message (`shopping_request`) names the reply language and, for Suggest More, the items already shown: the 7B model follows the last message better than the system prompt. Each press shows a random ~70% of the fridge (in the request) and of the user's taste hints (in the prompt, to weigh together: likes, staples, saved favorite meals with their items, habits, patterns and high-rated items; `pick_input` in `services/shopping.py`), so suggestions follow each user's own input instead of one fixed list; recent meals aren't in the prompt. Limits are in every press: health rules, the avoid list, dislikes and low-rated items. So is the latest weekly analysis's nutrient line when it ran in the last 7 days (#207): it follows the nutritional-gaps wording in the profile and supplements section and says lacking nutrients are worth buying for and more-than-enough ones aren't, naming nutrients only, so the model picks the products (`NUTRIENT_LINE` in `services/personas/shopping.py`, built on `marked_nutrients` in `services/knowledge.py`, which the suggestions' line uses too); with no recent analysis, or nothing marked, the prompt is as before. The prompt asks for about 10–15 items. Fridge items left out of a press may come back, and the dedupe drops them. The prompt test seeds the draws (`SHOPPING_SEED`), so runs compare.

**Weekly Analyst persona** (#206): `POST /meals/weekly-review` reads the meals logged in the 7 days up to today and replies through Ollama structured outputs (`WEEKLY_SCHEMA` in `services/weekly.py`): the narrative, the 4 scores, then two nutrient lists, `lacking` and `more_than_enough`, each limited by the schema to `NUTRIENTS` in `models/nutrients.py` (energy, macros, fiber, sugar, salt, fats, vitamins, minerals; most important first, and the prompt says so), so it can name a nutrient, never a food. The prompt asks it to mark a nutrient only when the week's meals make it confident and to leave the rest out, with no cap; code keeps listed names only, each once, in the list's order, and drops one marked both ways (`clean_nutrients`). The review screen gets the narrative and scores; the lists stay on the server. Each analysis covers the 7 days up to the day it ran (`period_start`, `period_end` on `weekly_summaries`) and is filed under the calendar week it ran in (Monday to Sunday by the server's local date: its ISO week, `week_key`, `week_of` in `services/weekly.py`). A new one replaces only the one from the same week, so the latest run of a week wins and a week that has ended keeps its last one as that week's copy; analyses older than six months are deleted (at a new analysis and at the server's start). Rows from before step 5 keep the week they were filed under; there is no unique key, so old rows sharing a week all stay until a new analysis in that week replaces them. The screen shows the latest one run in the last 7 days. Without a meal in those 7 days the analysis doesn't run: 422 with a fixed message, and the Weekly Summary page shows a pop-up that says so (`ConfirmDialog` with `notice`). A reply that can't be read gets a fixed 500 and keeps nothing; Ollama unreachable gets a lyric. `GET /meals/weekly-review/status` gives `{nudge}`: true when a meal of those 7 days was logged or changed (`meal_history.updated_at`, set by `PUT /meals/{id}`) after the latest analysis, or there is none; Settings' Weekly Summary button and the page then show "Get your weekly analysis!", which clears once the analysis runs.

**Suggestion + Analyst + Shopping** share `backend/services/knowledge.py`.

**Prompt style:** state each rule once, in the prompt that owns it, as a positive instruction with a short reason, not a growing list of bans and special cases. Anything code can verify (fridge membership, JSON shape) is checked in code, not by asking another persona to police it.

## Key Rules

- **Health rules**: injected into every LLM prompt silently. Never surface them to the user.
- **Avoid list**: hard ban. Never suggest avoided ingredients. Code matches it by exact name only (shopping dedupe, suggestion fallback): a user who bans "Peynir" and then sees "Beyaz peynir" bans that too or states a habit ("no cheese, milk included"); code doesn't guess which products an item is in.
- **Fridge constraint**: suggestions use only the inventory. Nothing is assumed: basics (salt, oil, spices) and long-life items (flour, sesame, oats…) are logged like anything else, usually in the 🫙 Pantry group. A planned Fridge quick-add button will make logging them easy. Water is a utility like electricity and gas: recipes may list it and the check skips it. The suggestion prompt doesn't mention water, so the model isn't drawn to serving it on its own. Ingredient names in the meal JSON must match the inventory as written, one item per name (a cut or form like "rolled" goes in the ingredient's `prep`), so the code check can compare them. The check matches exact names (`same_name`: case, Turkish letters and plurals only), like the avoid list and the shopping dedupe: an extra or missing word can be another product ("Cheese" isn't "White cheese", "Poached egg" isn't "Egg"), so code never guesses.
- **Date and country**: today's date and the optional Country from Settings → Profile (`user_profiles.country`, list in `utils/countries.js` with ISO 3166-1 alpha-2 codes) go into the shopping and suggestion prompts (`format_today`), so "in season" means something. The selector lists "Germany (DE)" and shows only "DE" once chosen; the saved value is the name. The profile text the analysts read leaves the country out.
- **Context length**: every Ollama call sends the same `num_ctx` (`OLLAMA_NUM_CTX`, 8192 by default, `_options` in `services/llm.py`). Chat history is about 6000 tokens and Ollama's own 4096 drops the oldest messages silently; one value for all calls keeps Ollama from reloading the model. The KV cache fits a 6 GB GPU (`docs/SETUPALL.md`, Step 1).
- **Timeout**: every Ollama call waits up to `OLLAMA_TIMEOUT` seconds (150 by default, `config.py`) to connect and between a reply's bytes. A JSON reply comes all at once, so a model that thinks first must finish within it (raised from 120 for the model tests, #178).
- **Thinking**: `OLLAMA_THINK` (`true` or `false`, `config.py`) sends Ollama's `think` field with every call that has no think value of its own (below); unset sends none, so each model keeps its own default, since Ollama refuses the field for a model that can't think, except the default model (`DEFAULT_MODEL`), which runs with thinking off (`DEFAULT_THINK`).
- **A model per task or language** (#192): `OLLAMA_MODEL_<KEY>` with its own `OLLAMA_THINK_<KEY>` gives a task (`MODEL_TASKS` in `config.py`: chat, suggestion for the draft and the reply text, review, analyst, shopping, plan, weekly) or a reply language (en, tr) its own model. A call uses its language's model, else its task's, else `OLLAMA_MODEL`, and that model's own think value, else `OLLAMA_THINK`, else the default above (`model_for` in `services/llm.py`, resolved once when a call starts); every call site names its task and language. The model picker's file comes first (below), then `.env`, then the default. Two models that don't fit the GPU together reload at each switch (`docs/SETUPALL.md`). Candidate models and how to compare them: `docs/MODEL_TESTS.md` (`tools/model_battery.py` runs the same prompt tests for one model, `prompt_check.py --model` and `--think` for one test; the prompt test runs on the app's picks and labels the run with them, unless `--model` gives one model for every call; with `--data`, which needs `--model`, a test writes its inputs and the model's outputs to `tools/runs/models/`, and `tools/compare_runs.py` builds a blind A/B page from them, #178).
- **Model picker** (#240): `python -m tools.model_picker` (from `backend/`) serves one page on 127.0.0.1 only (`--port`, 8765 by default; no other address) with a dropdown per task and reply language from Ollama's `/api/tags`, each with "default (.env)", and a think switch (default / on / off) only for models whose `/api/show` capabilities list `thinking`. Save checks the body against that list (fixed 422 messages, no echo), refuses a non-local Host or Origin (403), and writes `backend/model_settings.json` (git-ignored, `MODEL_SETTINGS_PATH` in `config.py`) atomically. `routes()` in `services/llm.py` reads it on each call, parsing again only when its modified time changes (`services/model_settings.py`), so no restart: a key it sets replaces that key's `.env` route whole (an entry without think falls back to `OLLAMA_THINK`), a missing file means none, and a broken or invalid one keeps the last good settings with a warning. Tests point it at a temp folder (`conftest.py`), and `prompt_check.py --model` reads no file.
- **CORS**: configurable via `CORS_ORIGINS` env var (comma-separated).
- **Request limits**: every field a request carries, in its body, path or query, has a limit: text and lists a length, numbers a range (ids, prep time, profile age, height and weight, amounts), a free-form meal (menu, "Today I ate" version) a size, and text in a path the length of its matching body field. A whole request body has a size limit too (413), counted as it arrives whether or not the request declares its length (`BodySizeLimit` in `main.py`, a pure ASGI middleware that keeps nothing past the limit). They are named constants in `models/limits.py` with the field types built on them (`Name`, `Text`, `Note`, `SizedList`, `Id`, `SessionId`…), far above real use: they stop abuse and mistakes, so a long chat message, a big bulk shopping list and a long menu still work. Change a number there, nowhere else, and give a new request field one of those types: a test walks the app's routes (`test_every_request_field_has_a_limit`) and fails on a field without a limit. A request over a limit gets 422. A typed chat message over its limit, or a chat socket frame over its size (refused before it's read), gets a short note in the reply language (`TOO_LONG_TEXTS` in `routers/chat.py`), reaches no model and isn't saved. Request bodies are typed (favorites and session messages included: `FavoriteIn` in `models/meal.py` ignores the editor's extra fields).
- **Refusals and error replies**: a request the server refuses for its content gets 422 everywhere (an unknown group, a blank name, nothing to update), with a fixed message. A validation reply says where and why (`loc`, `msg`) without sending the input back (`validation_error` in `main.py`). An error reply never carries an exception's text: that goes to the server log, and the user gets a fixed message (`SUGGESTIONS_FAILED`) or a lyric. Replies leave out the account's internal id.
- **API docs**: `/docs`, `/redoc` and `/openapi.json` are served only when `API_DOCS=true` (off by default, `config.py`; `docs_url`, `redoc_url` and `openapi_url` are `None` otherwise in `main.py`).
- **Auth**: a name and a PIN, set with `manage.py add-user` or `set-pin` (both ask for the PIN, hidden, when `--pin` is left out); `users.is_admin` (`add-user --admin`) is checked by no endpoint today and is reserved for admin-only features; tokens live in memory, so a restart logs everyone out. An open app returns to the login screen with a note at its next refused request, or when its chat socket can't reopen. A token never goes in a URL, since URLs end up in logs: REST calls send it in `Authorization`, and the chat socket in its `Sec-WebSocket-Protocol` header as `bearer` then the token (`socket_token` in `auth.py`, the one header a browser lets a page set on a WebSocket); the server checks it before accepting, accepts with `bearer`, and refuses any other header, `?token=` included (4001). Each login is its own session: Logout ends this device's on the server too (`POST /auth/logout` through `revoke_token`, 204 also for an unknown or already ended one), so its token stops working on REST and on the chat socket, while the user's other devices stay logged in. The app clears its stored session before the call, so the device logs out even when the call fails; the chat socket checks the token when it opens, and the tab that logs out closes its own. PINs are stored as salted scrypt hashes (`scrypt$n$r$p$salt$hash`, OWASP-aligned cost in `SCRYPT_*` in `auth.py`), checked off the event loop and with `hmac.compare_digest`; an unknown name is checked against a dummy hash, so timing doesn't tell names apart. Plain SHA-256 hashes from before scrypt still log in, and that login re-hashes them, like any hash at an older cost. New or changed PINs take 6-10 digits, digits only since the login screen opens the number pad (`pin_problem`); PINs set before the rule still log in until `set-pin` replaces them, and login takes names up to 100 characters and PINs up to 64 (422 beyond). Failed logins are counted in memory per name on each client IP, one counter per pair, so typos on a shared device don't lock other users there and nobody can lock a user out of their own device: repeated failures get 429 with `Retry-After`, the wait growing with each further one (exponential backoff), and the PIN isn't checked while locked; each attempt counts before the check, so parallel requests can't slip past, a success clears the count, and a quiet spell forgets it (the `LOGIN_*` limits in `auth.py`). The login screen shows the wait (CORS exposes `Retry-After`). Tests hash at a tiny cost (`conftest.py`) unless marked `real_scrypt`.
- **Demo user**: only created when `DEMO_USER=true` (empty PIN), and the empty PIN logs in only while it's on, so a leftover demo account is locked once it's off. It's a normal user, never an admin (a start with it on clears the flag from one an earlier version made). A newly created demo account gets a starter fridge (`DEMO_FRIDGE` in `models/ingredient.py`, basics included). Never enable it on a reachable instance.
- **Language**: the UI is English only; the setting changes AI replies. User data is often Turkish and pulls a 7B model toward Turkish, so every user-facing prompt ends with a `FINAL REMINDER` restating the language directive. Code-built text in replies (e.g. prep plan labels) follows the same setting, and so do units.
- **Theme**: Settings → Theme (orange default, then green, teal, blue, purple: hues spread around the wheel, each nudged warm, all WCAG AA) changes only `--accent`, `--accent2`, `--secondary` / `--secondary-soft`, the assistant bubble `--bubble` and the prep plan's dish colors `--dish-1` … `--dish-4` (`index.css`, `:root[data-theme=…]`). Use those variables or `secondaryColor`, never a hard-coded accent hex. `--dish-1` is the accent and the other three are hues spread around the wheel from it at the accent's lightness (the secondaries fail AA on the bubble and share the accent's hue), kept away from the delete red and the missing-item yellow, each AA on its bubble (a theme test checks the contrast). A plan in the new format (`⏱ Plan (` heading, `utils/prepPlan.js`) gets a thin bar per dish down the left of its lines, ↳ lines included, and the dish name on a time line in the same color; dishes take colors in order of first appearance and a fifth reuses the first. Older plans and lyric fallbacks render as plain Markdown, and nothing is added to the plan text. Semantic colors never follow the theme: red (`colors.danger*`) means delete/remove, health-rule priorities are a traffic light (red top priority, yellow care a lot, green don't really care), plus expiry warnings, stars and the meal icon's readiness ring (`--c-ring-ready` / `--c-ring-missing` on a `--surface` tile: the text colors in dark at 2px, livelier ones in light at 3px (`--ring-w`) so yellow stays yellow; a theme test checks 3:1 in dark and 2.3:1 in light). Saved as the `theme` preference and cached in `localStorage` (`utils/theme.js`).
- **Appearance (light / dark)**: Settings → Appearance: Auto (follows the device live, default), Light, Dark (`utils/appearance.js`, `useMode()`), saved as the `appearance` preference and cached per device like the theme, applied before the first paint as `data-mode` on `<html>`. Every color is a CSS variable in `index.css` with a dark value (`:root`, today's look, also the fallback) and a light one (`:root[data-mode="light"]`: warm, soft neutrals, an oat page and cream panels, never stark white; and `[data-mode="light"][data-theme=…]` per theme: each accent is its dark hue darkened in OKLCH to WCAG AA on the page, the panels and the bubble, a pale bubble, dishes AA on it; `--secondary` is shared). Semantic colors are variables too (`--c-*`, used through `colors` in `styles/common.js`): they follow the mode, never the theme. Style files use these variables, never a new hex (white text on a filled button excepted); a theme test checks light contrast and that Settings' swatches match the accents. The Logo takes the mode's palette.
- **Styling**: Tailwind CSS v4 (`@tailwindcss/vite`) reads the same tokens through `@theme` in `index.css` (`bg-surface`, `bg-surface-2`, `text-fg`, `text-fg-muted`, `border-line`, `text-accent`, `bg-secondary`, `text-danger` …), and `dark:` follows `data-mode`. Its base reset (preflight) is off until the shared `src/components/ui/` components (shadcn CLI, `components.json`, `@/` = `src/`), so existing inline styles look as they did; the app's own page-wide rules sit in `@layer base` so utilities win over them. New UI uses Tailwind classes; existing components keep `*.styles.js` until their screen is redone. Motion moments are keyframes in `index.css`'s `@theme` (`animate-dash`: the Suggest cloche dashes in on a tap; `animate-pop`: a revealed option pops up), always used with `motion-safe:` so the phone's reduce-motion setting turns them off.
- **Supplements today**: a daily supplement counts as taken and an occasional one as not, unless the user marked it today (the supplements button in "Today I ate"). `supplement_daily_log` stores only a mark that differs from that (a daily one skipped, `taken = 0`, or an occasional one taken), and `TAKEN_TODAY_SQL` in `services/context.py` gives today's state to `/profile/supplements/today` and the prompts, so a skipped daily one reads as not taken.
- **App settings vs food preferences**: settings stored as preferences (`SETTING_KEYS` in `services/context.py`: language, theme, appearance, weekly-summary toggle) are kept out of prompts.
- **Database path**: a relative `DATABASE_PATH` counts from `backend/`, not from the folder the server or `manage.py` was started in (`resolve_database_path` in `config.py`), so a start from another folder can't open a new, empty database there. The server's start prints the full path and schema version (`describe_database`, #216).
- **Database migrations**: schema changes are numbered steps in `MIGRATIONS` (`database.py`), run in order at start and recorded with `PRAGMA user_version` (#209). Each step runs in one transaction with its number, so it's applied whole or not at all, and a step that fails stops the start with its message. A brand-new database gets `_SCHEMA` and the latest number at once. To change the schema, update `_SCHEMA` and add a step at the end (columns through `_add_column`, which skips one that's there); never edit a step that has shipped. Step 1 is the one-time regroup, step 2 the changes from before the numbers, step 3 the clean-up of rows left without their parent row (`PRAGMA foreign_key_check`, and child rows under another user's chat or supplement) before foreign keys were enforced, step 4 a favorite's icon (`favorite_meals.emoji`, #244), step 5 a weekly analysis's days and nutrients (`weekly_summaries.period_start`, `period_end`, `lacking`, `more_than_enough`; older analyses get the 7 days up to the day they ran) and a meal's last edit (`meal_history.updated_at`, #206). The app's connections (`get_db`) and `manage.py`'s turn `PRAGMA foreign_keys` on, so a delete goes children first (a chat's messages and suggestions, a supplement's daily log, a user's rows before the user) and a row can't point to a parent that doesn't exist; the migration connection leaves it off, so a table rebuild in a step isn't blocked. `manage.py backup-db` keeps a backup only when it passes SQLite's integrity check. Before the first pending step, a database with data is backed up through SQLite's backup API (`_backup_before_migration`: `<name>_before_migration_<time>_v<version>.db` beside the database, checked the same way, the newest `MIGRATION_BACKUPS_KEPT` kept, #216); a backup that fails stops the start before any step runs. Only the server start migrates (`init_db`, with the clean-up of old chat sessions and the demo user): `manage.py` commands call `check_schema`, which stops with "start the server once" when steps are pending and sets up only a brand-new database (the set-up guide creates the first user before the first start).
- **Line endings**: `.gitattributes` normalizes to LF in repo, CRLF on Windows checkout.

## Shared Components

**Logo** (`frontend/src/components/Logo.jsx`) — the cloche mark, and with `withName` the "break FAST" wordmark (Unbounded, outlined into paths, so no font loads), on the login screen and at the left of the tabs, with the name beside the mark wherever the row has room for it (`useNameFits` in `App.jsx` measures the free space as the row resizes; the tabs show icons only below 760px). Everything brand starts in `frontend/src/brand/brand.js` (shapes, light and dark palettes, the icon background `#0E1A13`, which is also the manifest and `theme-color` color); `npm run icons` renders the outlined wordmark, the PWA icons and favicons in `frontend/public/` and the master SVGs in `frontend/brand/` (its README lists every place the name and colors live). Brand colors are fixed and never follow the accent theme, except "FAST" in the app's wordmark, which takes the theme's `--accent` (the master files keep the brand orange).

**ConfirmDialog** (`frontend/src/components/ui/confirm-dialog.jsx`) — the pop-up "Are you sure?" window (Tailwind, no library): the question, Cancel (focused when it opens), then the action (red with `danger`). Tab stays inside, Esc, Cancel or a tap outside closes it, and the focus goes back. Used for Settings' "Delete meals older than one month". With `notice` it is a note with nothing to decide: only the action button (its OK), focused; used for the Weekly Summary's "no meals in the last 7 days".

**ConfirmPrompt** (`frontend/src/components/ConfirmPrompt.jsx`) — the inline "Are you sure?" box: the question, Cancel, then the action (red with `danger`, for a delete; the theme color otherwise). Used before both Delete all buttons (shopping list, shopping suggestions) and Settings' Bring back. A single delete (× on a row) doesn't ask.

**Units** — source of truth: `backend/models/units.py` (`UNIT_PAIRS`: each English unit paired 1-1 with its Turkish match, plus `UNIT_ALIASES` like "gr" → g), mirrored in `frontend/src/utils/ingredients.js`. Edit both locations. Spoons and glasses have one fixed size in both languages (`UNIT_ML`: tsp 5 ml … glass / su bardağı 200 ml), stated in the suggestion prompt and shown only in the editor's open unit list, so an amount means the same in either language; "cup" is deliberately not a unit (a US cup is 240 ml). Units follow the AI language (English list by default, Turkish in Turkish mode): the suggestion prompt lists them, and stored meals keep their units as written while known ones are shown in the current language (`localizeUnit`; the prep-plan input does the same). The frontend reads the language from `utils/language.js` via `useLanguage()`, set at login and by the Settings toggle.

**Unit memory** (`frontend/src/utils/ingredients.js`) — `unitsFor(language)`, `resolveUnit(name)` (localStorage memory → smart keyword default from Turkish or English names → pcs / adet, shown in the current language), `rememberUnit(name, unit)`.

**Ingredient groups** — source of truth: `backend/models/ingredient.py` (INGREDIENT_GROUPS), mirrored in `IngredientPanel.jsx`. Edit both locations to change groups. A new item (Fridge add, bought from the shopping list) gets the group picked in the add panel ("Auto" picks none), else the user's own pick for the name (`ingredient_group_memory`), else the built-in food list's, else Other (`services/ingredient_groups.py`). Names match exactly (`same_name`), so "Free-range eggs" goes to Other until the user moves it once. Memory records every name added to the Fridge with its group (a planned quick-add lists what the user had before), and only rows marked `picked` count as the user's choice: a group picked in the add panel, or given in an edit when code wouldn't give the name that group (a move, or a renamed item keeping its group), never a group code chose. A new pick unmarks earlier picks for the same name, and a group code chose never overwrites a pick.

**Food list** (`backend/data/ingredient_catalog.json`) — about 600 common breakfast and home-kitchen foods by group, each `{"en": [...], "tr": [...]}`: the first name in each language is the display name (a planned Fridge quick-add can show it), the others are spellings of the same food. Written for the project and edited by hand. A name that could be two groups ("Pepper": spice or produce) stays off it, so its item goes to Other. Tests check that no name is on it twice, every food has both languages and `DEMO_FRIDGE` matches it. A one-time pass at start (`PRAGMA user_version` 1) marked old memory rows as picks unless they say Other (the old code saved the Other default on every add, so those stay plain names) and moved Other items the list knows.

## Glossary

**Makespan** — total wall-clock time from first task to last in a cooking plan.

**Warm prior** — stated habit treated as a starting assumption, updated by observed behaviour.

**Favorites / Explore modes** — favorites optimises for familiar meals; explore finds novel meals adjacent to the user's taste profile.
